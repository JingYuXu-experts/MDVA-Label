# 代码优化报告：mdva 桌面查看器的拖动重绘路径

## 背景与症状

用户反馈：「拖动的时候都在卡顿，里面的内容视觉上一直在卡顿卡顿，非常不好用」。
先量再改：把 `render.render_item`、`ImageTk.PhotoImage`、控件 `destroy` 都挂上计数器，
在真实数据（`data/aerospace`，勾选 7 路，单格 360×260）上模拟 40 步拖动。

**关键发现：瓶颈不在算，在 Tk。** 单格渲染实测只要 0.3–13 ms（7 路合计约 40 ms），
但旧实现把「重画」写成了「销毁整张网格 → 重建 Frame/Label → 重新分配 PhotoImage」，
而 `ttk.Scale` 每移动一个像素就派发一次 command。于是：

| 基线（旧实现） | 数值 |
| --- | --- |
| 每步中位耗时 | 72.6 ms |
| 每步 p95 | 78.6 ms |
| 40 步总耗时 | 2919 ms |
| 渲染调用 | 280 次（40 × 7，全部格子每步重来） |
| 新建 Tk 图片 | 280 张 |
| 销毁控件 | 560 个 |

72 ms/步 = 约 14 fps，而且事件是排队处理的：拖一次攒几十个事件，界面就一直在补
「几十步之前的那个游标位置」——视觉表现正是用户说的"一直在卡顿"。

基准脚本：`code_optimization/bench_drag.py`（`python code_optimization/bench_drag.py` 复现）。

---

## 【优化版本】v1 —— 消除重复劳动（算法层）

### 【优化内容】

1. **控件只建一次**。拆成 `rebuild()`（勾选、单格尺寸变化时才销毁重建）与
   `paint()`（只更新已有格子的图片）。原因：控件的销毁/重建/重排是每步 72 ms 里的主要开销。
2. **只重画"会随游标变"的格子**。新增 `_moves_with_cursor()`：时序、事件、多视图
   （立方体/视频）跟游标有关；单帧图像无关，拖时间轴时重画它纯属浪费。
   原因：这是选择性重画，把每步的固定工作量从 N 降到"真正会变的数量"。
3. **按 (切片号, 时间窗, 样式, 变换, 尺寸) 做键值去重**。同一状态重复请求直接跳过。
   原因：多个入口（滑块、下拉、勾选）会在同一帧里请求同一次重画。
4. **原地 `photo.paste(img)` 复用 Tk 图片对象**，只在尺寸变化时才新建。
   原因：每步 7 张新 Tk 图片是纯垃圾生成。
5. 顺带修掉一个真 bug：排队中的重画请求如果落在 `rebuild()` 拆掉控件之后，
   会对已销毁的控件调 `config` 抛 `TclError` 并把异常甩进 Tk 回调。
   现在 `rebuild()` 会作废排队请求，`paint()` 用 `winfo_exists()` 跳过死控件。

### 【优化后性能】

- 每步中位：72.6 ms → **24.4 ms**（快 66%）
- 每步 p95：78.6 ms → 25.6 ms（**最坏一步从 79 ms 降到 26 ms**，抖动基本消失）
- 40 步总耗时：2919 ms → 959 ms
- 渲染调用：280 → 200 次（跳过 3 个单帧图像 × 40 步 = 120 次）
- 新建 Tk 图片：280 → **0 张**；销毁控件：560 → **0 个**

### 【和基线对比】

- 快约 **3.0×**；验证结果：**PASS** —— 同一游标位置下，7 格画面与基线**逐像素一致**
  （把 Tk 图片写成 PPM 再比字节；`np.asarray(PhotoImage)` 只会得到 0 维对象数组，
  拿它比"一致"是自欺欺人，第一版基准就栽在这里）

## 【优化版本】v2 —— 事件合并 + 静态组归零（并发/调度层）

### 【优化内容】

1. **重画请求合并到下一帧**：`request(kind)` 只记意图（`cursor` < `all` < `build` 取上界），
   用 `after_idle` 挂一次 `_flush`，期间再来多少个滑块事件都不重复排队。
   原因：拖动的 40 个事件应该画 1 次，不是 40 次。
2. **合并时取最高级别**：中途来了"重建"级请求不会被降级成普通重画。
3. **`_moves_with_cursor` 在纯图像组上退化为零工作量**：整组都是静态图时，拖游标一步都不重画。

### 【优化后性能】

- 40 次拖动事件（中途不泵事件）：总 **114 ms**，实际重画 **5 格**
  （基线做同样 40 次要 2919 ms、280 格）
- 最坏情况——整组 60 张分割静态图，拖一步：
  基线 **351.7 ms / 重画 60 格** → 优化后 **0.9 ms / 重画 0 格**（约 **390×**）
- Python 侧峰值内存：一轮拖动 14 KiB（不再有每步 7 张 Tk 图片的分配）

### 【和基线对比】

- 一次真实拖动（40 事件）从 2919 ms 降到 114 ms，约 **25×**；验证结果：**PASS**

---

## 最终总结（已达最大迭代次数：2 轮）

- **最佳版本**：v2
- **总体提升**：每步 72.6 ms → 24.4 ms（v1，3.0×）；一次拖动 2919 ms → 114 ms（v2，约 25×）；
  纯静态组每步 351.7 ms → 0.9 ms（390×）
- **优化策略**：消除重复劳动（控件复用 + 选择性重画 + 键值去重）→ 事件调度合并（`after_idle`）
- **正确性**：逐像素一致 PASS；界面测试 17 项通过（含新增 6 项：选择性重画、请求合并、
  过期请求不崩、参数置灰、一键演示落在联动窗、高级面板默认收起）
- **适用场景**：任何"一个滑块驱动多面板重画"的界面；格子越多、静态格子越多，收益越大
- **权衡**：
  - `paint()` 跳过静态格子依赖 `_moves_with_cursor` 这个显式判据。将来若给单帧图像加
    "按时间切换不同文件"的能力，这个判据必须同步改，否则拖动时那些格子会不更新。
  - 合并到 idle 意味着最快约一帧一次重画（本机约 40 ms/次，25 fps）。要更跟手只能
    把渲染搬到后台线程 + 双缓冲，那是另一量级的改动，本次没做。

### 进一步建议（本次未做）

1. 渲染移到工作线程，主线程只做 `paste`（可再消掉 24 ms 的同步阻塞）
2. 拖动时先画低分辨率缩略图、松手后补全分辨率（渐进式）
3. 时序格子缓存已算好的降采样金字塔，避免同一窗口反复抽稀
